actmaton

Build while you sleep. Steer when you wake.
寝ている間に作り、起きたときに舵を取る。

actmaton は、ローカルファーストな自律コーディングエージェントです。 Rust / Tokio 製のコントロールループが GitHub Copilot SDK を通じてモデルを動かし、 GitHub Issue に書かれたタスクを、隔離された git worktree の中で実装し、テストし、 ドラフト PR として提出します。

人の役割は、個々の操作を承認することではありません。 方向を決める（steering）ことと、PR をマージするかどうか判断することだけです。 それ以外の「課題を見つける → 実装する → テストする → PR を出す」は actmaton が自律的に回します。

actmaton の目標は「良い自律コーディングエージェントになること」。 その最初の実証として、actmaton は自分自身のリポジトリを開発し続けています（dogfooding）。 初期の実行ターゲットは 16 GB の Apple Silicon Mac です。

概念の地図

登場人物は4つだけです。それぞれの担当を押さえれば、全体が読めます。

あなた（人）方向を決める。Issue コメントで舵を取り、PR のマージを判断する。
→
propose（監査役）リポジトリを監査し、次のタスクを Issue として起票する。コードは書かない。
→
run（実装役）Issue を1件受け取り、worktree の中で実装とテストを行う。
→
loop（自律反復）propose と run を繰り返し回し続ける司令塔。止まる条件は機械的に決まっている。
  • PR はドラフトで作られます。 マージできるのは人だけです。actmaton が勝手にマージすることはありません。
  • バックログと判断の記録は GitHub にあります。 Issue がタスク、コメントが指示、PR が成果物、という役割分担です。
  • 安全は「承認」ではなく「ガードレール」で確保します。 書き込み範囲の制限、シェルの検査、停止条件などが自動で働きます（安全装置）。

コマンドリファレンス

actmaton のコマンドは4つです（ほかに開発用 spike があります）。

コマンド何をするか
actmaton run <issue> [--dry-run] GitHub Issue を1件実装します。Issue の本文（とコメント）を読み、専用の worktree とブランチを作り、モデルに実装させ、最後に actmaton 自身が cargo test を実行して合否を判定します。ブランチの push や PR の作成はしません（それは loop の仕事です）。
actmaton run <issue> --dry-run モデルを呼ばずに、セッションへ渡すプロンプトと権限ポリシーの要約を表示します。「何をさせようとしているか」を事前に確認するためのモードです。
actmaton propose リポジトリを監査し、次のタスクを1件、GitHub Issue として起票します（ラベル actmaton-proposal）。コードは変更しません。監査の仕組みはpropose の監査を参照してください。
actmaton loop [--max-iterations N] [--max-failures N] [--budget-minutes N]PR #35 マージ待ち propose と run を自律的に繰り返します。テストが通った変更は push され、ドラフト PR が自動で開かれます。詳細は自律ループの仕組みを参照してください。
actmaton --version バージョンを表示します（例：actmaton 0.1.0）。
run の引数は Issue 番号（17 や #17）でも、Issue の URL でも構いません。

自律ループの仕組みPR #35 マージ待ち

actmaton loop は、人が1件ずつ指示しなくても開発が進み続けるためのコマンドです。 各イテレーション（繰り返しの1回）で次のように動きます。

タスクの選び方

  1. open している Issue のうち、最も古いものを選ぶ。
  2. ただし hold ラベルが付いた Issue と、この loop の実行中にすでに処理した Issue は除く。
  3. 選べる Issue が無ければ、propose が新しい Issue を起票し、それを次のイテレーションで処理する。

停止条件

暴走を防ぐため、止まる条件は最初に機械的に決まっています。開始時にすべてログへ出力されます。

条件意味（既定値）
--max-iterations Nイテレーション回数の上限（既定 5）
--max-failures N連続失敗の上限（既定 2）。失敗した Issue を同じ実行で再試行することはない
--budget-minutes N実行時間の予算（既定 240 分）

レポート

イテレーションごとに、使ったモデル、合否、PR のリンク、1行要約が actmaton-runs/loop-*.md に追記され、標準出力にも表示されます。 進捗はこのレポートとドラフト PR を見れば追えます。

ループが作る PR はドラフトです。マージは常に行いません。マージは人の判断です。

Steering の方法

steering（舵取り）は、actmaton の作業に人が介入するための正規の経路です。 主な手段は GitHub Issue のコメントです。

Issue コメントで指示するPR #22 実装済み

  • run は Issue の本文だけでなくコメントも読み、セッションに渡します（時系列順、直近20件まで）。
  • 本文とコメントが矛盾する場合は、コメントが優先されます。本文を書き直さなくても、コメントで上書き指示ができます。
  • loop の実行中にコメントを書けば、次のイテレーションから反映されます。

なぜこの仕組みが要るのか：以前は run が本文しか読まなかったため、コメントに書いた誘導がセッションに届かず、同じ Issue で3回やり直しになったことがあります（Issue #14 の実装時）。PR #22 でこの穴を塞ぎました。

hold ラベルで止める

「この Issue にはまだ触るな」という場合は hold ラベルを付けてください。 loop は hold 付きの Issue を選択しません。付け外しは即座に効きます。

やり直し・方向修正の頼み方

  • 部分的な修正：対象の Issue にコメントで具体的に書く（「〜ではなく〜してほしい」）。次に run / loop がその Issue を扱うときに反映されます。
  • 丸ごとやり直し：PR を閉じ、Issue に何が違ったかをコメントしてから再実行させます。前回の作業が worktree に残っている場合、leftover ガードが勝手に消さずに停止するので、人の確認なしに作業が消えることはありません（安全装置）。
  • 大きな方向転換：新しい Issue を立てるか、既存 Issue のコメントで方針を示します。actmaton は Issue の内容を正として動きます。
繰り返しになりますが、マージだけは常に行います（人）。 actmaton の権限の範囲は「ドラフト PR を出すところまで」です。

propose の監査PR #33 マージ待ち

propose は「次の機能を思いつく」仕組みではありません。コードベースを監査し、 証拠のある課題だけを Issue 化する仕組みです。設計の参考は shadcn/improve の「監査役はコードを書かず、計画だけを作る」という考え方です。 狙いは、コーディング AI にありがちな「機能とコードが増える一方で肥大化する」流れを抑えることです。

監査カテゴリ

カテゴリ見るもの
正確性バグ、仕様と実装の食い違い
性能無駄な処理、不要なコスト
テストテストの無いモジュール、検証の穴
技術的負債と簡素化重複、デッドコード、早すぎる抽象化、削除できるコード
ドキュメントドキュメントとコードの不整合（ドキュメントずれ）
方向性新機能の提案。別枠で扱い、扱うのは以下で制限される

方向性（新機能）の提案は、健全性タスクとは別枠です。1回の propose で起票できるのは最大1件で、 しかもリポジトリ内の証拠（TODO、ロードマップ、繰り返し現れる回避策など）を引用できた場合に限ります。 一般論的なアイデアは vet で落とされます。

vet（精査）と前提チェック

  • 証拠の引用の再読：発見が引用する file:line を実際に読み直し、引用文がその場所にあるか確認します。合わなければ落とします。
  • 前提チェック：「X が無い」「Y のテストが無い」のような現状についての主張は、ファイルを実際に確認して裏取りします。思い込みの前提で Issue が立つことを防ぎます（過去に「テストが無い」という誤った前提の提案が出たことがあります）。
  • 落とした発見は捨てずに却下台帳へ記録します。

却下台帳

actmaton-runs/propose-ledger.jsonl は、vet で落とした発見とその理由の記録です。 次回の propose はこれを読み込み、同じ発見を再提案しません。 「一度検討して却下したものが何度も浮上する」という無駄を断つための仕組みです。

起票される Issue の形式

propose が作る Issue は、実装役が迷わないよう計画形式で書かれます。

  • 現在の状態（証拠つき）
  • 対象範囲（In scope）と対象外（Out of scope）
  • 検証コマンド（正確な実行方法）
  • 完了条件（機械的に判定できる形で）
  • STOP 条件（「X の場合は止まって報告すること」）

安全装置

actmaton は無人で動く時間が長いため、安全は人の承認ではなく自動のガードレールで確保します。

装置内容
worktree スコープの権限 セッションが読み書きできるのは、そのタスク専用 worktree の中だけです。パスを正規化した上で判定し、worktree の外へのアクセスは拒否されます。シェルコマンドも、worktree の外を指すものは拒否されます。git push はセッションからは実行できません。
シェルガードPR #19 実装済み シェル経由のファイル編集（ヒアドキュメント、ファイルへのリダイレクト、sed -i、tee、dd of= など）を決定的に検出して拒否します。拒否するときは理由をモデルへフィードバックとして返すので、セッションは「黙って諦める」のではなく write ツールに切り替えて続行できます。/dev/null への出力や 2>&1 のような読み取り専用の形は通します。
leftover ガードPR #10 実装済み 同じ Issue を再実行したとき、前回の worktree やブランチが残っていた場合の処理です。綺麗で先行コミットが無ければ作り直しますが、変更が残っている・コミットが進んでいる場合は、実行を拒否して何も消しません。人の作業や前回の成果が自動で消える事故を防ぎます。
自己修復PR #31 マージ待ち 実装後に cargo test が落ちたら、失敗出力を次のセッションに渡して直させる、というフィードバックループです。再試行は最大2回まで。直らなければ worktree を残したまま失敗として終了します。
プロンプト側の編集ルールPR #18 実装済み セッションへの指示でも、ファイル編集は write ツールで小さく行うこと、シェル編集をしないこと、拒否されたら黙って終わらず手段を切り替えること、を明示しています。ポリシー（拒否側）とプロンプト（指示側）で同じルールを両面からかけています。

サンドボックスについて（正直な現状）

本来の本命は、OS レベルのサンドボックスでセッションの手足を囲うことです。 GitHub Copilot SDK にはそのための設定（SandboxConfig：Seatbelt / Bubblewrap 等で囲い、 認証情報の隠蔽やネットワーク遮断まで担う設計）があることが分かっています。 しかし Rust SDK がその型を公開していない不具合のため、まだ使えません。 上流に github/copilot-sdk#2922 として報告済みで、修正の監視を続けています。

つまり現状のシェル権限は「文字列ベースの判定＋ガード」という暫定の仕組みであり、OS サンドボックスの代替ではありません。 だからこそ今は、worktree スコープ、ドラフト PR、マージは人、という多層の決まりとセットで運用しています。 上流の修正が出れば、サンドボックス方式へ移行する計画です。

モデル

actmaton のセッションは、役割ごとに違うモデル設定を使えます。 「自己評価は甘くなりがち」という問題への対策として、実装する側と評価する側を分けるのが基本方針です。

役割ごとの既定値

役割既定のモデル理由
実装（run、自己修復を含む） Fusion、ティア Standard Fusion はタスクに応じてモデルを自動で振り分ける仕組みで、コスト面の割引もあるとされています。タスクごとに実際に選ばれたモデルはイベントとログで確認できます。
提案（propose）と評価（vet） gemini-4-hydrogen 実装側とはモデルのファミリーを変え、評価の独立性を保ちます。

設定の優先順位フラグ化は Issue #36

  1. CLI フラグ（--model / --fusion-tier）— 導入予定（Issue #36）。
  2. 環境変数（ACTMATON_MODEL、ACTMATON_FUSION_TIER、役割別の上書き）— 現行の仕組み。PR #30 マージ待ち
  3. 組み込みの既定値（上の表）。

ログには、どの経路で決まった設定かも併せて記録されます。

フォールバック

指定したモデルがプランの都合などで使えない場合、actmaton はエラーで死なず、 既定の自動選択（auto）に切り替えて実行を完走し、その旨をログに明記します。 実際に使われたモデル（resolved model）はセッションのイベントから取得してログに残すので、 「auto の中身がサーバー側の都合で変わった」ような変化も後から追えます。

正直な注意点：上位の Fusion ティアである High（HydraFusion）は、 現在のアカウントのプラン（Copilot Pro）でも権限が無効で使えませんでした。 またカタログに載っていないモデル名（例：claude-opus-*）は実行時に「not available」になります。 既定値が Standard と gemini-4-hydrogen なのは、実際に動作確認が取れた範囲で選んでいるためです。 プランが変われば使える範囲も変わる可能性があるので、その場合は再調査が必要です。

ログとレポート

実行の記録は、リポジトリの隣の actmaton-runs/ ディレクトリに残ります。 「actmaton が何をしたか」は、まずここを見れば分かります。

ファイル中身
issue-<n>-<時刻>.log（run ログ） 1回の run の記録。セッションの手順、権限判定の結果（許可／拒否とその理由）、最終メッセージ、差分の統計、テストの合否、自己修復の試行、使われたモデルとフォールバックの有無が入ります。
propose-<時刻>.log（propose ログ） 監査のプロンプトとモデルの応答、参照チェック・前提チェックの結果、発見ごとの処分（起票／見送り／却下）が入ります。
loop-<時刻>.md（loop レポート）PR #35 マージ待ち loop のイテレーションごとの記録。Issue、モデル、合否、PR リンク、1行要約と、最後に止まった理由が入ります。
propose-ledger.jsonl（却下台帳）PR #33 マージ待ち vet で落とした発見とその理由の台帳。次回の propose が読み込み、再提案を防ぎます。

用語集

steering（舵取り）
人が actmaton の方向を決める行為全般。Issue コメントでの指示、hold ラベルの付け外し、PR のマージ判断が含まれます。個々の操作の承認とは別の概念です。
vet（精査）
propose の発見を起票前に検証する工程。引用されたコードを読み直し、前提を裏取りし、通らない発見を落とします。「懐疑的に当たる」のが仕事なので、発見を出した側とは別の工程として分けています。
却下台帳（rejection ledger）
vet で落とした発見と理由を記録したファイル（propose-ledger.jsonl）。次回以降の propose が参照し、同じ提案の蒸し返しを防ぎます。
leftover ガード
再実行時に前回の worktree／ブランチが残っている場合の保護処理。作業が残っていたら消さずに停止します（PR #10）。
hold（ホールド）
GitHub ラベルの名前。このラベルが付いた Issue は loop の選択対象から外れます。人のための手動ブレーキです。
dry-run（ドライラン）
モデルを呼ばずに、プロンプトと権限ポリシーの要約だけを表示する確認モード（actmaton run <n> --dry-run）。コストをかけずに「何をさせるつもりか」が確認できます。
Fusion（フュージョン）
Copilot のモデル自動振り分けの仕組み。ティアは Standard（Auto Balance：タスクに応じてモデルを選び、今回のテストでは gpt-6-luna が選ばれた）、High（HydraFusion）、Max（HydraFusion Max）があります。ただし High / Max は現在のアカウントでは使えません。
自己修復（self-repair）
テストが落ちたとき、失敗出力を次のセッションへ渡して直させる仕組み。上限回数つきです（PR #31 マージ待ち）。
dogfooding（ドッグフーディング）
自分の製品を自分で使うこと。actmaton は自分のリポジトリの開発に actmaton 自身を使い、その過程で弱点を洗い出しています。
ガードレール
「やってよい範囲」を自動で囲う仕組みの総称。権限スコープ、シェルガード、停止条件などが該当します。安全を人の注意力ではなく構造で確保するための考え方です。
